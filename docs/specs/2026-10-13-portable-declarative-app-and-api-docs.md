# Portable declarative apps and generated app-author API docs
- Status: Ready for implementation
- Date: 2026-10-13
- Source: `/brainstorm` request on 2026-10-13:
  - "Make the frontend language declarative like SwiftUI, and have a deterministic tools/scripts to generate the doc API (markdown) … in api-docs/ (auto generated, no LLM) -> to be the latest API for user/agent to work on without scan the source code"
  - "make it easy to use like SwiftUI. The idea: user only code once, and can build in multiple platform, no need to add too much platform-specific code"
  - Owner clarification during the session: "This docs is only for user to implement their app (to use the declarative, how to use it), not internal api docs". Also: "index is autogenerated too".
  - Evidence: workspace on `main` at `4d75722` (clean tree), plus a check of the installed toolchains (stable 1.99, 1.88, no nightly).
  - Builds on [2026-10-12-declarative-views.md](2026-10-12-declarative-views.md), which is already implemented.
  - Shares the gallery size cap with [2026-10-13-metal-gpu-renderer.md](2026-10-13-metal-gpu-renderer.md). The owner settled the shared cap after a cross-spec review on 2026-10-13.

## Outcome and current state

**Beneficiaries.** Application authors, and the coding agents that work for them. Authors write one SwiftUI-style view program that compiles unchanged on every OS. An agent learns the whole app-author API from `api-docs/`, without reading the toolkit source.

**Current state (verified):**
- **The declarative layer exists.** `choscorui-compose::view` (about 12k lines) has `View::body`, `Cx`, `State`, `Binding`, `Memo`, tuple children, `ForEach`, `Dynamic`, `Branch`, chained modifiers in `Styled`, presentation modifiers, toasts, and `ViewHost`. `docs/guide.md` documents it by hand.
- **The app layer is macOS-only.**
  - `App`, `AppContext`, `Scene`, and `WindowId` are `#[cfg(target_os = "macos")]` (`crates/choscorui/src/lib.rs:41-44`).
  - The prelude re-exports `MenuBarModel`, `MenuCommandId`, `MenuEntry`, `MenuItemState`, `MenuSpec`, and `WindowOptions` from `choscorui_macos`, under the same cfg (`lib.rs:84-88`).
  - On another OS, an app's `main` does not compile without `cfg` gates.
- **The gallery shows the cost.**
  - `gallery/src/main.rs` puts `cfg` on `main` and most of its modules.
  - `gallery/src/settings.rs` and `gallery/src/strings.rs` have `cfg(target_os)` items.
  - `gallery/src/ui/app.rs` (520 lines) imports `choscorui::platform::{MenuBarModel, MenuCommandId, …, StatusItem, notification_permission, post_notification, request_notification_permission, screen_visible_frames, url_handler}`. It matches numeric `MenuCommandId` constants in one handler, and reads `window.last_paint()`.
- **App code has friction** (counts in `gallery/src/ui`):
  - 48 `Configured::custom`/`try_custom` escape hatches for hosted controls that have no view, for example Toaster, StackedContainer, Avatar, ScrollBar, Counter, Toolbar, and the toolbar Input.
  - 64 `.expect(` calls, for example `IntegerRange::new(..).expect("demo ranges are valid")` in `gallery/src/ui/pages/range.rs:21`.
  - 63 `Cx<'_>` spellings. No lint forces them: `&mut Cx` already compiles.
- **No generated API docs.**
  - Stable rustdoc 1.99 refuses `--output-format json` without `-Z unstable-options` (checked in the session).
  - The dependency rule (`docs/architecture.md#dependency-rule`) bans new crates such as `serde` and `syn` from the build graph.
- **Size budget.** The release gallery is about 3,141,900 bytes (2.996 MiB) against `size.choscorui-gallery_mib <= 3` in `bench/budgets.txt`. The 2.96 MiB baseline in `docs/performance.md:92` is stale. The headroom is about 3 KB, and the binary grows in 16 KiB page steps.
- **CI** runs on `macos-15` and `macos-15-intel` only (`.github/workflows/ci.yml`). Installed rustup targets: `aarch64-apple-darwin`, `x86_64-apple-darwin`, `x86_64-pc-windows-gnu`.

**Desired state.**
- One app source, using only `choscorui::prelude` (plus documented extension points), compiles for macOS, Windows, and Linux with no `cfg` and no `choscorui::platform` import.
- It runs on macOS. On other OSes `App::run`/`App::start` return `AppError::Unsupported` until a backend lands.
- `api-docs/` holds generated Markdown for exactly that app-author surface, with a doctested example for each view and modifier. CI fails when the docs are out of date.

## Decisions and requirements

### Decision ledger (all settled by the owner in the session)

| ID | Decision | Answer |
| --- | --- | --- |
| Q1 | Platform scope | Portable API in the facade. macOS stays the only backend that runs. Other OSes compile, and `run`/`start` return `AppError::Unsupported`. Rejected: a new Windows or Linux backend (too large), a headless runner (extra scope). |
| Q2 | Doc engine | rustdoc JSON from one **pinned nightly**, rendered by a std-only tool. Rejected: `RUSTC_BOOTSTRAP` on stable (the Rust project says not to use the flag), a hand-written source parser (brittle with glob re-exports and `macro_rules!`). |
| Q3 | Doc scope | **App-author surface only:** the prelude plus an explicit allowlist of extension points. This replaced an earlier "all facade modules" answer after the owner said the docs are not internal API docs. |
| Q4 | Freshness | `--check` in the CI `check` job fails when `api-docs/` differs from a regeneration. |
| Q5 | Ergonomic gaps to close | All four: commands as views, a view for every public hosted control, no-unwrap builders, persisted state and window restore. |
| Q6 | Breaking changes | Clean break before 1.0. Remove the replaced APIs, migrate the gallery, guide, and tests, and list each removal in the release notes. No deprecation period. |
| Q7 | Doc layout | Topic files, assigned by a checked-in config. The generated `README.md` index lists every item. |
| Q8 | Examples | A doctested `# Examples` block is required on every in-scope view type, `ViewExt` modifier, and `App`/`Scene`/`AppContext` entry point. |
| Q9 | Portable bar | All gallery code except the native verification harness (`autopilot.rs`) has zero `cfg(target_os)` and zero `choscorui::platform`. The portable layer therefore covers the status item, URL-handler query, and notification permission. |
| Q10 | Size budget | Shared 3.25 MiB cap with the Metal renderer spec. Offset growth first. Then set `size.choscorui-gallery_mib` to the measured size plus one 16 KiB page, never above 3.25. If it would exceed 3.25, shrink code. This replaced an earlier "hold ≤ 3, ask before changing" answer. |

### R1. Portable app layer (Q1, Q6, Q9)

**Where code lives:**
- Platform-independent descriptions go in core: window options, the menu model that a backend receives, notification, clipboard, and dialog requests, and status-item descriptions.
- View-facing APIs go in compose: command menus as views, presentation modifiers, and storage.
- The facade owns backend selection. It is the only crate where `cfg(target_os)` picks an implementation. Keep it in one private module, for example `crates/choscorui/src/backend/`.
- App code and compose branch on `capabilities()`, never on `cfg`.
- `choscorui-macos` maps the core descriptions to AppKit. It may depend only on core (`bylaw.toml`).

**Facade API on every target:**
- `App`, `AppContext`, `Scene`, `WindowId`, `AppError`, and `WindowOptions` exist on every target and are in the prelude.
- `App::run`/`App::start` return `AppError::Unsupported` (new variant) when no backend exists for the target. The error has a lowercase `Display`, as `docs/versioning.md#error-reporting` requires.
- `capabilities()` keeps its present behavior: `BackendCapabilities::none("headless")` off macOS.
- Remove the macOS re-exports `MenuBarModel`, `MenuCommandId`, `MenuEntry`, `MenuItemState`, `MenuSpec`, and `WindowOptions` from the prelude. Remove `App::commands(menu, handler)`. Migrate every caller (Q6).
- `choscorui::platform` stays as an escape hatch on macOS. It is not in `api-docs/` or the guide's main path.

**Services an app reaches without `platform`:**
- The services are clipboard, notifications (post, and query or request permission), status item (like SwiftUI `MenuBarExtra`), URL-handler query, and open/save dialogs.
- Each one is gated by a `BackendCapabilities` field. Add fields as needed; the struct is `#[non_exhaustive]`.
- Each service returns a domain error, such as an unsupported error, when its capability is `Unsupported`. It never panics.
- A view action reaches the services through the environment (`Env`). App-level code reaches them through `AppContext`.
- Open/save dialogs follow the binding style of the existing presentation modifiers. For example, `.file_importer(presented, types, on_result)` and `.file_exporter(...)` are SwiftUI-like.
- The exact names follow toolkit naming. Document them in `docs/guide.md`.

**Gallery migration:**
- `gallery/src/main.rs`, `settings.rs`, `strings.rs`, `catalog.rs`, `cli.rs`, `page.rs`, and `ui/**` use only the portable layer.
- Native readback (`window.last_paint()`, the first-frame report, and the scripted checks) moves into `gallery/src/autopilot.rs`, or behind a portable hook. Only `autopilot.rs` may use `cfg(target_os)` or `choscorui::platform`.
- Off macOS, the gallery `main` prints the `AppError::Unsupported` message and exits non-zero.

### R2. Commands as views (Q5)

- Remove `App::commands(menu, handler)` and the numeric command IDs in app code.
- An app declares menus with views, for example `App::commands(|| (CommandMenu::new(t!("menu.file"), (Button::new(t!("menu.quit"), …).keyboard_shortcut(…), Divider::new(), …)), …))`, or as a scene modifier.
- Each item carries:
  - its own action closure
  - live label and live disabled and checked state (`Toggle`/`Binding<bool>` items for check marks)
  - an optional shortcut
  - submenus
- Live state that an item read rebuilds or updates the native menu. This keeps the behavior of the present menu closure, which rebuilds on change.
- The facade lowers the view description to the core menu model with generated IDs, and sends each chosen ID back to its closure.
- A Command-key shortcut runs from the keyboard as it does today (`docs/guide.md`, "Commands, shortcuts, and menus").
- The gallery's theme and language menus, page navigation, new window, close, and quit use this form.

### R3. A view for every public hosted control (Q5)

- Add views for every public hosted control in `choscorui-controls` that apps can reach today only through `Configured::custom`/`try_custom`. This includes at least Toaster, StackedContainer, the Avatar group, ScrollBar, Counter (NumericDisplay counter), Toolbar and its items, and the toolbar Input.
- A test enumerates the public hosted controls and fails when one has no view. The control catalog in `crates/choscorui-controls/tests/catalog/` is the list. Put the test beside the existing gallery coverage test or in compose tests.
- `Configured` stays as the extension point for third-party `CustomControl`s.
- The gallery has no `Configured::custom`/`try_custom` calls for built-in controls after the change.
- Keep focus order, keyboard activation, and accessibility semantics the same as the configured form. Golden files must not change except for an intended, reviewed change (CLAUDE.md).
- Update `docs/controls.md` in the same change.

### R4. No-unwrap constructors (Q5)

- Add builder forms for values that today need `.expect`. For example, `Slider::new(label, value).range(0..=100).step(1).page(10)` and the same for `SpinBox`, `RangeSlider`, `Dial`, and `Progress`. Find other `.expect(` sites in `gallery/src/ui` and cover each one that comes from a toolkit constructor.
- An invalid combination is clamped to the nearest valid value. It is also reported as a `ViewError` through `ViewHost::take_errors` and `App::on_error`. It never panics.
- The fallible constructors (`IntegerRange::new`, …) stay for callers who want the `Result`.
- Not covered: `.expect` on app-owned data, such as `store.insert(..)` in `gallery/src/ui/pages/display.rs:216`. That is app logic.

### R5. Persisted state and window restore (Q5)

- `App::id("com.example.app")` (or an equivalent) gives the reverse-DNS app id. The settings file path comes from the existing `user_settings_path(app_id)`.
- `cx.stored(key, default)` returns a `State<T>` whose value is loaded from `Settings` and written back on change, like SwiftUI `@AppStorage`. It supports the `SettingValue` kinds (`bool`, integers, floats, `String`, lists, `Rect`).
- Settings errors follow the existing load lifecycle (`docs/guide.md#load-lifecycle`), with `load_or_recover` semantics. They reach `App::on_error`, and the state then uses its default. No panic.
- Writes are batched. Save at most once per event-loop turn, and at quit. The atomic write path (`.tmp`, fsync, rename) does not change.
- `Scene::restore_geometry(key)` saves the window geometry on close and restores it at open. It uses the existing `WindowGeometry::store`/`restore`/`fit_to_screens` and the backend's screen frames internally. The app calls no screen API.
- Optional migrations: the app can pass a `SettingsSchema` (version, defaults, migrations) to `App`.
- The gallery's `settings.rs` path logic and its `CHOSCORUI_GALLERY_SETTINGS` override keep working. Example: an `App` method that sets an explicit settings path.

### R6. Generated app-author API docs (Q2, Q3, Q4, Q7, Q8)

**Tool:**
- New std-only workspace crate `tools/api-docs` (package `choscorui-api-docs`), with no dependencies. Add it to the `[workspace] members`, to `bylaw.toml` (it depends on no workspace crate), and to `docs/architecture.md`.
- It runs `cargo +<pinned-nightly> rustdoc -p choscorui --lib --target aarch64-apple-darwin -- -Z unstable-options --output-format json`.
- One file in `tools/api-docs/` pins the nightly, for example `tools/api-docs/nightly.txt`. The tool reads the pin from it.
- The tool checks the JSON `format_version` against one constant. On a mismatch it fails and tells the user to bump the pin and the constant together.
- It parses the JSON with a hand-written std-only parser.
- Modes:
  - Default: write `api-docs/`.
  - `--check`: regenerate in memory. Exit 1 and list each stale, missing, or extra file when `api-docs/` differs.
  - Error exit 2 when the toolchain or rustdoc fails, with the command and its stderr.

**Scope (Q3):**
- In scope: every item that `choscorui::prelude` exports, plus the non-prelude items that `tools/api-docs/topics.txt` lists. That list is the allowlist of extension points.
- Expected extension points: `CustomControl`, `ControlView`, `Configured`, `Canvas`/`CanvasContext`, the `MeasureContext`/`PaintContext`/`ControlContext` that custom controls use, `Settings`/`SettingsSchema`/`SettingValue`, and `capabilities()`/`BackendCapabilities`/`Support`.
- Not in scope: core internals (`Tree`, `NodeId`, `LayoutEngine`, …), raw hosted controls that have a view, `choscorui::platform`, and the root re-exports kept for compatibility.

**Layout (Q7):**
- `tools/api-docs/topics.txt` is plain text with one `<topic> <item path>` per line, plus comment lines. Expected topics: `app`, `state`, `layout`, `controls`, `modifiers`, `presentation`, `styling`, `text`, `custom`, `other`.
- The tool fails when:
  - an in-scope prelude item has no topic
  - a line names an item that does not exist
  - an item is listed twice
- Output:
  - `api-docs/README.md`, the generated index. It has a header line saying the file is generated and must not be edited by hand, with the regenerate command. It states that every example assumes `use choscorui::prelude::*;`. It lists the topics, then each item with its kind and the first sentence of its doc comment, linked to its anchor.
  - One `api-docs/<topic>.md` per topic. For each item: the import path, the full signature, the full doc comment, and inherent methods with their signatures and docs. A view type also lists the modifiers it gets from `ViewExt` by reference. Trait items list their in-scope implementors.
  - `modifiers.md` holds the `ViewExt` methods, grouped by the topics config.
  - A topic file over a size limit splits by item kind. Choose a limit that keeps each file readable in one agent read, about 2,000 lines.

**Content rules (Q8):**
- The tool fails and lists each item that has no doc summary.
- It fails and lists each in-scope `View` type, `ViewExt` method, and `App`/`Scene`/`AppContext` public method whose doc comment has no `# Examples` section with a Rust code block.
- Examples are doctests in the crate that defines the item.
- Hidden setup lines (`# use …`) are dropped when rendered, as rustdoc does.
- Use `no_run` for code that starts the app.
- After R1, examples compile on any host.

**Determinism:**
- Same source plus same pinned toolchain gives byte-identical output.
- Items are sorted by name within a topic. Methods are sorted by name.
- No timestamps, absolute paths, hashes, or rustdoc IDs in the output. LF line endings, with one trailing newline.
- The output has no LLM step.

**Docs check interaction:**
- `scripts/check-docs.sh` keeps checking links and the reference design system name in `api-docs/`.
- It skips the sentence-length and banned-term checks there, because the text comes from source doc comments. Record the reason in the script header.
- Assumption: the generator writes only valid relative links. A unit test asserts that.

### R7. Docs and examples spelling

- Write `fn body(&self, cx: &mut Cx) -> impl View` in all docs, doctests, the guide, and the gallery. This replaces `Cx<'_>`.
- Update `docs/guide.md` to the portable API: commands as views, services, storage, restore, builders, and the new views. Link it to `api-docs/README.md` as the generated reference.
- Also update these docs:
  - `docs/architecture.md`: facade backend selection, the new crate, the portable descriptions in core
  - `docs/versioning.md`: stable surface, `platform` as the escape hatch, `AppError::Unsupported`
  - `docs/controls.md`
  - `docs/platform-macos.md`: capability values
  - `docs/README.md`
  - `docs/performance.md`: the size budget, its reason, and the measured baseline, if the budget changes (Q10)
  - `CONTRIBUTING.md`: install the pinned nightly, run `api-docs --check`, and regenerate after a public API change
- Gallery sample strings go through the catalogs in **en and vi only**. Ask the owner before adding a language.

### Non-goals

- A running Windows or Linux backend, or a headless runner.
- A macro DSL. `macro_rules!` sugar stays deferred, and proc macros stay banned.
- Generated docs for internal crates or `choscorui::platform`.
- A stylesheet file. The owner still defers it.

### Edge cases and failure behavior

- A pinned nightly that is not installed makes the tool exit 2 with `rustup toolchain install <pin>` in the message.
- A JSON format change makes the tool exit 2 and name the expected and actual `format_version`.
- A command menu item whose action panics is caught at the existing menu boundary and counted (`callback_panic_count`). The item stays usable.
- `cx.stored` with a value type that does not match the stored `SettingValue` falls back to the default and reports a `ViewError`.
- Two scenes restoring the same geometry key: the last window to close wins. Document this.
- A service call when its capability is `Conditional` (for example, notifications outside an app bundle) returns the domain error, and the gallery shows its message, as it does today.

## Constraints and risks

- **Repository rules (CLAUDE.md):**
  - Platform-independent policy goes in core, controls, or compose. App code branches on `capabilities()`. Fallible public APIs return domain errors.
  - `unsafe` only in `choscorui-macos/src/ffi/`, and each new AppKit call (status item, dialogs, menu mapping) goes through the `ffi` macros with a `SAFETY` comment. `cargo test -p choscorui-macos` must pass the header checks.
  - No suppressions. Delete code with its last caller.
  - Run the native smoke tests, the gallery, and autopilot one at a time.
  - Never claim VoiceOver, real input methods, clean install, or Intel verification from automation.
- **Dependency rule:** the new tool is std-only. The pinned nightly is a developer and CI tool outside the build graph, like clippy. State this in `docs/architecture.md#dependency-rule`.
- **MSRV 1.88:** all crates, including `tools/api-docs`, pass `cargo +1.88 check`. Only rustdoc JSON generation needs the nightly.
- **Size risk (high):** about 3 KB of headroom under 3 MiB, and a 3.25 MiB cap that this spec shares with the Metal renderer. Whichever change lands second measures on top of the first. Keep the growth small:
  - Make the new views thin over one shared generic mount path, for example backed by `Configured` internally.
  - Lower the commands with non-generic code.
  - Keep the storage code out of monomorphized paths.
  - Measure early with `choscorui-bench`.
- **Golden files:** new views must not change the existing goldens. Bless only an intended change, and call it out.
- **Breaking change (Q6):** bump the pre-1.0 minor version. The release notes list the removed `App::commands(menu, handler)` form, the removed prelude platform re-exports, and the moved `WindowOptions`.
- **Nightly pin upkeep:** bumping the pin can change the JSON format. The tool's version check makes this an explicit, reviewed change.
- **Deferred minor details (assumptions, not owner decisions):**
  - The exact nightly date: the newest nightly that builds the workspace at implementation time.
  - Exact type and method names: follow existing naming.
  - The topic file size limit: about 2,000 lines.
  - The exact service access shape on `Env`/`AppContext`.
  - None of these changes the scope or the acceptance criteria.
- **Not verifiable by automation:** VoiceOver reading of the new views and menus, real input methods, the notarized clean install, and Intel hardware need a person.
